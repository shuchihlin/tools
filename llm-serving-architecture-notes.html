How frontier LLMs are deployed and served

Session notes — mapping the legacy 3-tier web deployment model to modern LLM serving. August 2026.

1. From 3-tier web to LLM serving

What stays the same: the edge. GeoDNS/anycast routing to the nearest POP, TLS termination, API gateway doing auth, rate limiting, and quota. Requests are stateless HTTPS with streaming responses (SSE). Tier 1 is recognizable CDN/gateway territory.

What changes fundamentally:

Modern deployments also split prefill (prompt processing, compute-bound) and decode (token generation, memory-bandwidth-bound) into separate GPU pools, shipping the KV cache between them over RDMA.

2. Replica and KV cache — definitions

Replica = one complete copy of the model weights (hundreds of GB to TBs), loaded into GPU memory across however many GPUs it takes, plus the inference engine running them. Weights are shared, read-only, permanent. 100 replicas = 100 copies of the same weights, each serving its own set of users.

KV cache = per-request scratch memory. As the model processes tokens, each layer's attention keys/values are cached so each new token doesn't recompute them (memoization). Per-request, read-write, transient — created when a request starts, grows one token's worth per generated token, discarded (or briefly kept as a reusable prefix) when the response finishes. Can reach gigabytes for long contexts.

Rough replica sizing (FP8 weights, H100-class 80 GB GPUs): a 70B dense model fits in half to one 8-GPU node; a frontier MoE (~1–2T params) needs 16–32+ GPUs across 2–4 nodes. A 1,024-GPU cluster holds ~128–256 replicas of a 70B model, or ~32–64 replicas of a frontier MoE.

4. Consumer Claude app — full path

The desktop app is an Electron-wrapped web client. Conversations live in Anthropic's cloud backend (which is why the same history appears in browser, desktop, and mobile). The control plane (backend + DB, co-located, multi-AZ) and the inference plane (GPU datacenters, placed where power exists) are separate — tolerable because backend→inference is one RPC per turn against a multi-second GPU operation.

Per-turn sequence: client sends new message + conversation ID → backend reads history from DB → assembles full prompt → calls inference API → replica generates, tokens stream back → backend relays to client and writes both turns to the DB. The DB and the replica never communicate; both are passive backends of the app tier.

5. OpenClaw on LINE — same shape, different owner

The consumer chat backend is not publicly accessible. Developers use api.anthropic.com/v1/messages — which is the inference API: stateless, full-prompt-in / response-out, gateway in front of the replicas. Therefore OpenClaw must play the chat-backend role itself: store history per LINE user, reconstitute the full messages array every turn, persist the reply. Without that, every reply is amnesiac.

6. Failure and recovery

DB side (control plane): standard multi-AZ synchronous replication — AZ failure triggers automatic standby promotion in seconds-to-minutes, no data loss. Cross-region posture (backups vs async replica vs active-active) is not public for Anthropic. If the full region fails, the consumer product is down even though the GPUs are fine, because the backend must read the DB to assemble the prompt.

Inference side: when a replica dies mid-generation, its KV caches vanish with the HBM — never checkpointed (checkpointing GBs per request per token step would cost more than it saves). Recovery is not failover but full redo: resend the full prompt to another replica, prefill from token zero, regenerate.

User-visible consequences of a mid-stream replica death: a latency spike (full prefill + regenerating tokens already produced), and possibly a different answer — sampling is stochastic, and Replica B produces a new stream, not a resumption (some stacks force the already-streamed tokens as a prefix to hide this).

Blast radius asymmetry: one dead GPU kills one replica and ~100 in-flight requests, but the fleet self-heals in seconds — router marks it dead, traffic rebalances, requests retry. The boring SQL database is the actual single point of durable truth and gets all the failover engineering. The old rule survives intact: statelessness buys cheap recovery; state is where the engineering lives. The LLM stack made its enormous transient state (KV caches) disposable by design — that choice is what makes the whole thing operable.

7. Operational takeaways for OpenClaw

  1. Build the memory loop: store history per LINE user → load + append on each webhook → send the full messages array to /v1/messages → persist the reply. No history = amnesiac bot.
  2. Retries are your job: on API errors or broken streams, your code retries. Idempotent and safe since the request is stateless; cost is tokens and time.
  3. Prompt caching: long conversations resend an ever-growing prefix each turn. Use the API's explicit prompt caching (cache-control breakpoints on the stable prefix) to cut input-token cost — the KV cache mechanics turned into a billing optimization.
  4. Back up your store: unlike Anthropic's multi-AZ DB, your VPS has no built-in redundancy. If it dies, your users' histories die with it.
