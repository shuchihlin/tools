Claude Plugins & Skills — Reference Notes

Last updated: June 26, 2026

The two worlds (the root of all the confusion)

Claude.ai (cloud account) — reached via any browser (PC/Mac/phone) and the mobile apps (iPad, iPhone, Android). All the same account in the cloud. Anything installed while logged into Claude.ai syncs across every browser and mobile app on that account.

Claude Desktop (installed application on one computer) — the standalone app with Chat / Cowork / Code tabs. Plugins added here are saved locally to that machine. They do not sync to your Claude.ai cloud account.

These two worlds are invisible to each other. The word "Claude" gets used for both, which is what makes it confusing.

Why a desktop-installed plugin doesn't show up on iPad

Plugin installed on Claude Desktop (World 2, local). Question asked from the iPad app (World 1, Claude.ai cloud). Different worlds → the plugin simply isn't present in the iPad session. A built-in skill of the same name runs because it's the only one there — not because it "beat" the custom one.

To get a plugin onto iPad/web: install the marketplace + plugin again from within Claude.ai (log in via browser, install there; it then syncs to the iPad app on the same account).

Where plugin skills work, once installed in a given world

  • Marketplace plugins' skills work across all three surfaces of the world they're installed in: chat on web, the Chat tab in Desktop, and Cowork.
  • Hooks and sub-agents run only in Cowork (grayed out in chat).
  • Local-directory plugins (installed via terminal CLI /plugin marketplace add /path) work only in the CLI — the desktop UI can't register a local path.

Name conflicts & precedence (the important part)

Plugin skills are namespaced as plugin-name:skill-name. Because of that, they cannot truly conflict with built-ins — they coexist as separate addresses rather than one overriding the other.

So on desktop, where both a custom plugin and the built-in exist:

  • Typing the bare /morning-note → resolves to the built-in (default).
  • Typing /<plugin-name>:morning-note → resolves to the plugin's version.

It's not a fight the built-in "wins" — it's two different identifiers. The bare name just defaults to the bundled one.

The one case of genuine override

A same-named skill placed in personal (~/.claude/skills/) or project (.claude/skills/) scope does replace the bundled skill for the bare name.

Precedence order: enterprise > personal > project > bundled. Also: a skill beats an old-style command of the same name.

Two reliable levers to always hit your own version

  • Invoke the namespaced form: /<plugin-name>:morning-note.
  • Or give the skill a unique name (e.g. /morning-brief) so the short form is unambiguous and nothing shadows it.

Quick verification commands

  • Desktop app: Customize → Plugins shows installed plugins and their skills.
  • Terminal CLI: /plugins, or ls ~/.claude/plugins/.
  • /doctor (CLI) shows if skill descriptions are being truncated/dropped.

Caveat to carry forward

Most precedence behavior above is documented for Claude Code specifically. Whether the web/iPad chat / picker exposes the same plugin:skill namespaced syntax is less clearly documented — so after installing into Claude.ai, check the / menu on iPad to confirm the namespaced entry actually appears.
